# 业务规则如何进入标准本体

| 业务规则 | 标准载体与验证 | 边界 |
|---|---|---|
| R01 任务、BUG直接归属唯一 | OWL排他来源表达；SHACL xone、minCount、maxCount | 不自动改变来源 |
| R02 来源需求与项目同产品 | SHACL-SPARQL SameProduct | 不凭名称补关联 |
| R03 需求转项目人工判断 | 业务骨架保留的人工决策说明 | 不发明复杂度或周期阈值 |
| R04 阶段及合同可选 | OWL不要求项目必有阶段合同；SHACL只检查已出现对象 | 正例包含无阶段、无合同分支 |
| R05 不添加隐含直接关系 | OWL属性链只推导relatedProduct；测试断言不新增任务直接归属需求 | 不推断工单所属合同 |
| R06 计划合计等于合同金额 | SHACL PlanTotal、正数及金额必填 | 基于当前加载数据范围 |
| R07 不超付 | SHACL Overpayment；SPARQL按decimal汇总 | 无法证明系统外付款 |
| R08 OA与实际转账之后登记 | 明确记为外部事实边界 | 不由OWL推断OA或银行状态 |
| R09 续签关系与服务期间 | OWL不同合同身份；SHACL循环、同产品、有效结束日期（终止日期优先）先后及终止事实检查 | 新旧数据完整性仍依赖来源 |
| R10 状态独立 | 各类状态枚举独立SHACL约束；SPARQL单列BUG待关闭 | 不以关联对象完成推出本对象完成 |
| R11 对象稳定身份 | RDF IRI及OWL AllDifferent；源环境、记录ID注解 | 更名不合并对象 |
| R12 未知不等于否定 | OWL开放世界对照；RDF快照范围；SPARQL完整性未知时不绑定paid/unpaid | observedPaid仅表示当前加载明细合计 |
| R13 角色按对象区分 | 独立OWL对象属性、SHACL角色目标类与数量 | 未定义角色之间的自动继承 |
| R14 计划、实际分开 | 独立OWL数据属性和SHACL类型约束 | 不模拟完整写入历史 |
| R15 两种阶段不能混同 | OWL互斥类，HermiT矛盾反例 | 付款阶段不被当作项目实施阶段 |

`shapes.ttl`允许每个对象使用的业务属性是封闭的；类型与来源注解允许保留。RDFLib对无显式datatype的字符串与显式xsd:string的内部项比较有差异，状态枚举在SHACL中同时列出两种等价字符串写法，并有兼容性回归用例；未放宽状态业务范围。

标准模型不依赖旧JSON或自定义规则计算运行结果。首次词汇迁移参考旧定义，但标准文件可以脱离旧模型独立运行。已有导出中间图仅作为实例映射来源，不读取其金额汇总或旧规则问题列表来代替标准执行。

2026-10-09补齐：需求前期状态与类型匹配；主子任务同直接归属、两层及完成一致性；一需求一项目、一项目一合同与续签链不分叉；每条业务答案附相关SHACL状态和问题。数量口径已由用户明确确认，任务层级对齐当前SIDM约束，均放入SHACL，不固化为OWL永久限制。

运维合同付款：用户已确认录入即表示已付款。maintenance-contracts.rq通过SPARQL绑定有效合同金额为paid，并返回paymentStatus及paymentBasis；金额缺失、为零或负数时不生成已付款金额。项目合同仍按实际付款明细汇总。
