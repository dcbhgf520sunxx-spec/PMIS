1. 接入准备

接口根地址：https://gcglsys.znjs.com:9088/api/open/v1。测试环境请使用 SIDM 管理员提供的测试地址；下文路径均拼接在接口根地址之后。

地址、请求头和凭证分别放在哪里？

完整请求由三部分组成：接口地址 + 请求头 + 请求正文。不是把这三部分拼成一个网址。

  • 接口地址 = 根地址 + 业务路径。根地址末尾不加斜杠，业务路径以一个斜杠开头；不要重复拼接 /api/open/v1。POST、GET 是请求方法，不是地址的一部分。
  • 请求头是随请求发送的键值对。Authorization 是键，Bearer 实际凭证 是值；Bearer 后是一个英文空格，再接完整凭证，不带尖括号或额外引号。
  • 请求正文是业务参数 JSON，例如要查询哪条需求、由谁操作。它不放在请求头中。GET 读取的参数按手册要求放在 URL 的问号后。
根地址：https://gcglsys.znjs.com:9088/api/open/v1
业务路径：/requirements/operate
完整地址：https://gcglsys.znjs.com:9088/api/open/v1/requirements/operate
请求方法：POST

假设管理员给你的凭证为 EXAMPLE_TOKEN_NOT_VALID（仅演示，不可调用），在接口工具中这样填写：

填写位置名称填写内容

正文Body（JSON）使用下面的查询示例
{
  "operation": "QUERY",
  "sourceRecordId": "REQ-001",
  "operatorEmployeeNo": "EMP001"
}

REQ-001 替换为该接入系统已创建的需求来源编号，EMP001 替换为真实操作人工号。查询不传 idempotencyKey；新增、编辑等写入才需要。若工具使用“Bearer Token”鉴权选项，只填凭证本身，工具会自动加 Bearer，不要再重复添加。

先用连接测试确认配置

连接测试不需要正文和操作人工号，只需正确地址及凭证请求头。命令示例（把演示凭证替换为实际凭证）：

curl 'https://gcglsys.znjs.com:9088/api/open/v1/health' \
  -H 'Authorization: Bearer EXAMPLE_TOKEN_NOT_VALID'

在浏览器地址栏直接打开接口不会自动带上凭证，不能用它代替上述测试。手册链接则不需要凭证，可从新页签的地址栏直接复制给对接人员。

请求头格式

Authorization: Bearer <接入凭证>
Content-Type: application/json
  • 所有接口均需要启用且未过期的系统凭证。JSON 请求携带上述两个请求头；附件上传采用 multipart/form-data。
  • 凭证识别接入系统，operatorEmployeeNo 识别实际操作人。业务操作在正文中传工号，基础数据及附件读取在同名查询参数中传工号，连接测试不需要工号。
  • 操作人须为 SIDM 有效用户，并具备相应菜单、按钮及业务权限。有效系统凭证不等于具备任意业务操作权限。
  • 创建人、更新人由实际操作人工号确定，不能直接传 creator/updater 或内部人员 ID。提出人、提出组织属于业务信息，不要求是 SIDM 用户。
  • 每个系统只能通过自己的来源编号操作对应记录。系统编码不是凭证，不需要作为业务请求参数。

凭证仅保存在受信任服务端；接入系统负责可信地传递实际操作人身份。不要把凭证交给浏览器或普通用户，也不要写入 URL、日志或共享材料。凭证重置后须及时更新调用配置。

2. 通用约定

业务方法与路径支持动作
需求POST /requirements/operateQUERY、CREATE、UPDATE、CHANGE_STATUS、CHANGE_PRIORITY、DELETE
运维工单POST /work-orders/operateQUERY、CREATE、UPDATE、CHANGE_STATUS、DELETE
请求字段中文名必填说明
operation操作类型是动作，必须使用表中大写值
sourceRecordId来源记录编号是外部系统业务编号，1–100 字符；同一系统、同一业务类型内唯一
operatorEmployeeNo实际操作人工号是实际操作人的 SIDM 工号，1–50 字符
idempotencyKey幂等请求号写入必填逻辑请求唯一编号，1–100 字符；QUERY 不允许传
data业务数据随动作新增、编辑、状态或优先级变更时传；查询和删除不传或传空对象

不接受未声明字段。枚举使用 JSON 数字，不用数字字符串。所有业务日期使用 YYYY-MM-DD，并按上海时区解释。

成功回执

{
  "code": 0,
  "message": "success",
  "data": {
    "operation": "CREATE", "result": "CREATED",
    "sourceRecordId": "REQ-001", "targetId": 126
  },
  "requestId": "本次追踪号"
}

HTTP 200 且 code 为 0 表示成功。写入回执表示事务已提交，需要完整记录时再 QUERY。targetId 为 SIDM 内部记录 ID，后续业务请求仍使用 sourceRecordId。

result含义
CREATED / UPDATED新增成功 / 更新成功
STATUS_CHANGED / PRIORITY_CHANGED状态变更成功 / 优先级变更成功
DELETED / ALREADY_DELETED删除成功 / 已删除，无须重复处理
SKIPPED / FOUND无变化 / 查询成功

幂等与重试

  • 同一逻辑写入重试使用原 idempotencyKey、原操作人及原业务参数；成功请求再次发送返回原业务回执，附加 replayed: true，本次 requestId 不同。
  • 不同逻辑写入使用不同请求号；不能把业务编号当作所有操作共用的请求号。同请求号但内容不同返回 409。成功幂等记录长期保留，请求号不可循环复用。
  • 网络断开或 5xx 时使用原请求号重试；参数修正后使用新请求号。附件请求指纹包含文件内容、名称及类型。
  • 同一记录按业务顺序发送，等待前一请求返回后再发下一请求。并发排队不保证外部事件顺序。不支持批量或 UPSERT。
  • 删除为软删除，来源映射保留；不能以已删除记录的相同来源编号重新 CREATE。

3. 连接与基础数据

GET /health：携带系统凭证，返回 data.status = "healthy"、message = "连接成功"。它只验证凭证和服务连通性，不代表业务写入权限。

GET /reference-data?types=products,users,workOrderProblemTypes&operatorEmployeeNo=EMP001
{
  "code": 0, "message": "success",
  "data": {
    "products": [{"name": "示例产品"}],
    "users": [{"employeeNo": "EMP001", "name": "示例人员"}],
    "workOrderProblemTypes": [{"code": "PT001", "name": "日常操作"}]
  },
  "requestId": "本次追踪号"
}

按需传入 types，多个类型用逗号分隔。名称、工号、问题类型编码以接口实际返回为准。产品名称须精确匹配，改名后请更新映射；调用方须明确传入产品和负责人，不使用来源系统专属兜底规则。手册中的数据均为示例。

description需求描述string/null否基础富文本，危险标签会清理；与页面业务规则一致，受单次 JSON 请求体8MB上限约束
requirementType需求路径integer是1 上会立项、2 需求提报、3 预研、4 直接实施

初始优先级为低（0）；初始状态由 requirementType 决定：1→0、2→10、3→20、4→30。新增不能指定 status 或 priority。

UPDATE 允许上表字段，至少传一项，只修改传入字段；未传保持不变，仅标注 null 的字段可清空。进入实施路径状态 30–35 后不允许修改需求路径，其他状态修改路径会重置到对应初始状态。状态和优先级使用专门动作。

新增示例

{
  "operation": "CREATE", "sourceRecordId": "REQ-001",
  "operatorEmployeeNo": "EMP001", "idempotencyKey": "REQ-001-CREATE-001",
  "data": {
    "title": "采购审批流程优化", "description": "<p>增加审批提醒。</p>",
    "requirementType": 4, "productName": "示例产品", "ownerEmployeeNo": "EMP002",
    "submitterName": "示例提出人", "submitterDept": "示例组织", "submitDate": "2026-09-07"
  }
}

状态与优先级

状态代码名称（按顺序对应）
0 / 1 / 2 / 3上会评估 / 需求上会 / 上会通过 / 过会未通过
10 / 11 / 12 / 13提报评估 / 需求审批 / 审批通过 / 审批未通过
20 / 21 / 22需求验证 / 预研通过 / 预研不通过
30 / 31 / 32需求整理 / 实施中 / 试运行
33 / 34 / 35已完成 / 已完成未使用 / 暂停

CHANGE_STATUS 必传 data.status；先 QUERY 查看 allowedStatuses，只能选择当前允许的目标。

  • 目标 33、34：还须传 actualEndDate（实际完成日期，不晚于今天）和 completionStatus（完成情况，1–200 字符）。
  • 目标 35：还须传 pauseDate（暂停日期）。
  • 其他目标只传 status，不接受与该状态无关的附加字段。
{
  "operation": "CHANGE_STATUS", "sourceRecordId": "REQ-001",
  "operatorEmployeeNo": "EMP001", "idempotencyKey": "REQ-001-STATUS-001",
  "data": {"status": 35, "pauseDate": "2026-09-07"}
}

CHANGE_PRIORITY 传 data: {"priority": 0}，0 低、1 中、2 高，需具备需求优先级调整权限。

DELETE 不允许删除已关联项目或仍有未删除任务/Bug 的需求。

目标状态名称必填附加字段

6. 查询与修改示例

{
  "operation": "QUERY", "sourceRecordId": "REQ-001", "operatorEmployeeNo": "EMP001"
}

QUERY 的 data 返回 operation、result、sourceRecordId、targetId，以及相应业务字段（见需求/工单字段表）、status、statusLabel、allowedStatuses、状态附加字段。需求另含 priority。

通用返回字段

字段中文名类型说明
creator创建人object / null首次创建记录的实际操作人，包含 employeeNo（工号）和 name（姓名）
updater更新人object / null最近一次修改记录的实际操作人，包含 employeeNo（工号）和 name（姓名）
createdAt创建时间string记录在 SIDM 的创建时间，返回带时区的时间
updatedAt更新时间string记录在 SIDM 的最近更新时间，返回带时区的时间

创建人和更新人由请求中的 operatorEmployeeNo 自动记录，调用方不能传入或覆盖。新建时两者通常相同；后续修改后更新人会变化。历史记录无法解析人员时返回 null。

完整查询响应示例

  "message": "success",
  "data": {
    "operation": "QUERY",
    "result": "FOUND",
    "sourceRecordId": "REQ-001",
    "targetId": 101,
    "title": "示例需求",
    "status": 31,

可选空值为 null，业务日期格式为 YYYY-MM-DD，创建时间和更新时间为带时区时间。

allowedStatuses 示例：[{"value":31,"label":"实施中"},{"value":35,"label":"暂停"}]。它不是全部状态清单，而是该记录当前允许变更的目标。

7. 附件

须先创建业务记录。下列 {resource} 为 requirements 或 work-orders；路径中的来源编号须 URL 编码。

动作方法与路径参数
列表GET /{resource}/{sourceRecordId}/attachments查询参数 operatorEmployeeNo
上传POST /{resource}/{sourceRecordId}/attachmentsmultipart/form-data：file、operatorEmployeeNo、idempotencyKey
下载GET /{resource}/{sourceRecordId}/attachments/{attachmentId}/download查询参数 operatorEmployeeNo；返回文件流
删除POST /{resource}/{sourceRecordId}/attachments/deleteJSON：attachmentId（正整数）、operatorEmployeeNo、idempotencyKey

上传需要文件本体，不传下载 URL 或 Base64；multipart 的 Content-Type 和 boundary 由 HTTP 客户端生成，不要沿用 application/json 或手写 boundary。

curl -X POST 'https://gcglsys.znjs.com:9088/api/open/v1/requirements/REQ-001/attachments' \
  -H 'Authorization: Bearer <接入凭证>' \
  -F 'operatorEmployeeNo=EMP001' \
  -F 'idempotencyKey=REQ-001-FILE-001' \
  -F 'file=@说明.pdf;type=application/pdf'

上传成功回执增加 attachment: {"id":218,"name":"说明.pdf","size":1024}，使用该 ID 下载或删除。列表返回 data.attachments，字段为 id、original_name、mime_type、file_size、sort_order、creator_id、updater_id、created_at、updated_at、business_type、business_id，不返回内部存储回执；ID 字段仅供识别，不能用于冒充操作人。

单文件不超过 20MB，每条业务最多 10 个附件，文件名最长 255 字符。支持 JPG/JPEG/PNG/WEBP/PDF/DOC/DOCX/XLS/XLSX/PPT/PPTX/TXT/MD/ZIP，文件内容须与类型匹配。

上传失败或结果不确定时，使用同一请求号和相同文件重试，避免重复附件。下载失败按错误码重试，勿将下载接口当作永久公开附件链接。

8. 错误处理

{
  "code": 400, "message": "业务字段不正确", "data": null,
  "fieldErrors": {"title": ["标题不能换行"]},
  "requestId": "本次追踪号"
}

fieldErrors 仅在可定位到字段时返回；鉴权、路由参数和上传解析失败也会返回 requestId。保留实际收到的 HTTP 状态、message 和 requestId 供排查，不记录凭证或文件正文。

HTTP含义与处理
400参数、字段、状态或文件类型错误；检查 message、fieldErrors，修正后用新请求号
401凭证无效或过期，联系管理员
403系统停用或操作无权限，联系管理员
404本系统来源编号或附件不存在，检查目标
409来源编号重复、幂等内容冲突或并发数据冲突，查询后处理
413附件超过 20MB
500处理失败，保留追踪号；原请求号重试或联系管理员
502附件存储暂不可用，可重试读取

调用方应设置合理超时和有限次数重试，持续失败时联系 SIDM 管理员，不要无限重复调用。业务写入失败后不得仅凭发送成功判定业务完成。
